# SSP API coverage

The SSP accepts GraphQL requests at `/graphql/spark/rc`,
`/graphql/spark/2025-03-19`, and `/graphql`. Financial mutations and
owner-scoped reads require a valid bearer session. Cooperative withdrawal
quotes also require a session because they check leaf ownership. Challenge handlers and non-binding fee estimates are public. Receive quotes,
history, and webhook registration, listing, and deletion require a session.

The server accepts the aliases and compressed request bodies generated by the
Spark JavaScript SDK. This table states the current behavior. Unsupported
financial operations return an explicit error before saving a request.

| Operation | Status | Current behavior |
|---|---|---|
| `get_challenge`, `verify_challenge` | Supported | Single-use five-minute challenge and durable 24-hour session |
| `leaves_swap_fee_estimate` | Supported | Returns zero; startup rejects a nonzero `SSP_SWAP_FEE_SATS` |
| `request_swap` | Supported and tested | Verifies the funded outbound transfer and completes an atomic Swap V3 counter transfer from exact SSP leaves |
| `request_lightning_send` | BOLT11 and BOLT12 supported and tested | BOLT11 uses a preimage swap. BOLT12 verifies a completed Spark prepayment, tracks the LDK payment, and returns the prepayment after a final failure. |
| `lightning_send_fee_estimate` | Limited | Returns the current zero-fee policy; it is not a route estimate |
| `request_lightning_receive` | BOLT11 supported and tested | Creates a hold invoice for the wallet hash, redeems wallet-held operator shares with `REASON_RECEIVE`, commits Spark before the LDK claim, and reconciles missed events |
| `request_bolt12_receive` | Supported SSP extension and tested | Creates a fixed-value BOLT12 offer and credits the wallet with a deterministic Spark transfer after LDK receives the payment |
| `transfers`, `user_request` | Supported for SSP-created records | Returns owner-scoped durable swap, Lightning, and withdrawal state |
| `lightning_receive_quote` | Supported, zero fee | Issues a signed protobuf manifest and validates the wallet attestation, amount, recipient, network, expiry, and unique transfer ID |
| `static_deposit_quote`, `claim_static_deposit` | Supported when configured | Values an owned unspent UTXO after three confirmations, commits the Spark payout through operator consensus, and broadcasts a signed Bitcoin recovery transaction |
| Instant static-deposit operations | Implemented, opt-in | Signed quotes, immediate Spark credit, operator reservation, and confirmed Bitcoin recovery; bounded by configured limits |
| Cooperative-exit operations and fee quotes | Supported when configured | Estimates Bitcoin fees, reserves a payout input, verifies the conditional Spark transfer, signs and broadcasts the payout, and recovers Spark leaves after confirmation |
| `FetchCurrentUserToUserRequestsConnection` | Supported | Owner-scoped cursor pagination over durable requests, with type, status, and network filters |
| Wallet webhook operations | Supported | Owner-scoped subscriptions and durable signed delivery with retries |

## Tested Lightning receive flow

The current end-to-end flow is:

1. Authenticate a standard Spark SDK wallet with the SSP.
2. Call the SDK `createLightningInvoice` method. The wallet creates the
   preimage and stores its threshold shares with the Spark Operators.
3. Pay the returned BOLT11 invoice.
4. Poll the receive request until `TRANSFER_COMPLETED`.

The SSP redeems the shares only as part of the operators' atomic Spark transfer.
The removed SSP preimage extension is not required. Receive quotes use the shared Spark protobuf and signature domains. The
current receive and swap fee policy is zero; fee-bearing quotes remain unsupported.

`cargo regtest test` runs this flow on a fresh local regtest network through the
Rust Breez SDK at revision `c7eecfe`. It uses local Electrs for Breez chain
data, two SSP instances, and two `ldk-server` nodes. The wallets send and
receive BOLT11 payments between SSPs. Two wallets on the same SSP settle an internal BOLT11 invoice through Spark
without an LDK payment. A durable reservation prevents a concurrent external
HTLC from paying the same receive. The test has separate BOLT12 send and
receive flows. It checks Spark balances, offer IDs, LDK payment state, and
preimage hashes. The runner also checks send replay, rejected funding, invoice
expiry, and missed-event recovery after an SSP restart.

Send records use typed statuses and explicit links to their Spark funding.
The intent and idempotency key are durable before LDK submission. See
[submission recovery](LDK_GAPS.md#submission-recovery) for lost replies.

## BOLT12 settlement model

A BOLT12 offer does not give the SSP a payment hash before the invoice-request
exchange. Therefore, BOLT12 sends cannot use the BOLT11 hash-locked Spark
transfer. The wallet first sends a completed standard Spark transfer to the
SSP. The SSP then pays the offer. If Lightning reports a final failure, the SSP
returns the same amount with a deterministic transfer ID. This flow is not an
atomic swap. It depends on the SSP refund policy.

For receive, the SSP creates a fixed-value offer. `ldk-server` claims the
Lightning payment, and the SSP then sends the offer amount to the wallet. This
flow is also not atomic because `ldk-server` has no BOLT12 hold-payment API.
Reconciliation repeats the Spark payout safely after a restart. A blinded
route can report an inbound amount that is larger than the offer amount. The
SSP credits only the fixed offer amount.

## SDK compatibility

Cooperative withdrawals require `COOP_BITCOIN_RPC_URL` and a funded, dedicated
Bitcoin Core wallet. Without this configuration, the operations return an
explicit error. The SSP checks the sender, receiver, amount, leaf IDs, transfer
status, and connector inputs before it signs the Bitcoin payout. It stores the
signed transaction before broadcast and retries the same transaction after a
lost reply or restart. Completed requests and input reservations are durable.

Each payout uses one confirmed native SegWit input. Private-wallet reads use the dedicated SSP operator listener. With operator
authorization enabled, `SSP_INTERNAL_ALLOWED_IDENTITIES` must contain the
SSP's compressed identity key. Public wallet queries keep their privacy checks. Quotes expire after five minutes;
wallets can split leaves after a quote to separate the payout and fee. One
withdrawal per wallet can be pending at a time. Batching is not implemented. An admin can create one child transaction to
bump an unconfirmed withdrawal fee, with an explicit rate and maximum cost. See [deployment](DEPLOY.md#cooperative-withdrawals)
for funding and backup requirements.

MutinyNet uses `SIGNET` on the wire. The pinned JavaScript SDK fork maps SIGNET
correctly. The SSP accepts both `lntb` and `lntbs` invoices for TESTNET and
SIGNET sends, since some Signet clients use the older Testnet currency code. Released SDK versions without that fix cannot run
the complete MutinyNet Lightning test.

The pinned Breez SDK does not expose high-level BOLT12 send or receive methods.
Clients can use `request_lightning_send` with an `lno1` offer and an explicit
amount after they transfer the same amount to the SSP. They can use the
`request_bolt12_receive` SSP extension to create a fixed-value offer.

See [ldk-server compatibility](LDK_GAPS.md) for the complete backend boundary.

## Quotes, history, and callbacks

Receive quotes expire after five minutes. The attestor signs the payment hash;
that quote ID can bind only one receive. The SSP uses the signed transfer ID
for the actual payout. Lightning send estimates advertise zero user fees; the
SSP absorbs backend routing fees. They are not route quotations.

History accepts `first` (1–100), `after`, `types`, `statuses`, and `networks`.
Cursors bind the authenticated owner and a stable creation-time/ID order.
Terminal statuses come from durable settlement records. Pending swaps resume
claim checks after restart.

Register a webhook with `url`, `secret`, and `event_types`. Supported events:
`SPARK_LIGHTNING_SEND_FINISHED`, `SPARK_LIGHTNING_RECEIVE_FINISHED`,
`SPARK_COOP_EXIT_FINISHED`, and `SPARK_STATIC_DEPOSIT_FINISHED`. Subscriptions
do not replay earlier completions. Deliveries use JSON and
`X-Spark-Signature`, the hex HMAC-SHA256 of the exact HTTP body with the
subscription secret. `X-Spark-Event-Id` stays constant across retries.
Consumers must deduplicate that ID. Delivery is at least once, with persistent
backoff up to one day between attempts. Only successful HTTP status codes
complete a delivery; redirects are not followed.

Callback URLs must use HTTPS and resolve to public addresses. For a local
regtest callback, `SSP_WEBHOOK_ALLOW_LOCAL=1` permits HTTP loopback endpoints.
This exception is disabled outside REGTEST/LOCAL. Secrets are omitted from
subscription-list responses. A wallet can have at most ten subscriptions.

Confirmed deposits require the dedicated Bitcoin Core wallet configuration
used for withdrawals and the private operator RPCs in the pinned sources.
Their quotes deduct the fee for a 99-vbyte recovery transaction. Persisted
claims retry the same operator request and recovery transaction after a lost
reply. Static deposits do not automatically replenish Spark liquidity.

Deposit history reports `CREATED`, `SPEND_TX_CREATED`, `SPEND_TX_BROADCAST`,
and `SPEND_TX_CONFIRMED` from saved progress. The payout succeeds at broadcast;
confirmation tracking continues after a restart.

Swap V3 responses include the actual unsigned CPFP refund transaction and its
operator-verified adaptor signature. Direct refund fields are null because
this flow does not create them. Initial status is `OUTBOUND_TRANSFER_SENT`.
Old empty swap responses are repaired from the operator transfer when read.
The transfer expiry is returned when the operator supplies it.

Request `updated_at` values are saved when state or response data changes.
Reads, retries, and worker polls that change no data do not change the value.
For old records, migration uses creation time because the old server did not
save update times. Legacy withdrawal and instant-deposit records have no real
settlement data. Reads of those records, including a history page containing
one, return an error instead of fixed fees or empty transactions. New
cooperative withdrawals return their saved transactions and fees.

A receive quote without `x-partner-jwt` reports `NO_PARTNER_JWT`. If that
header is present, the quote reports `PARTNER_ATTRIBUTION_UNSUPPORTED` and
still contains no partner fee. This SSP has no partner registry or token
verification service; it does not claim to attribute a supplied token.

Instant static deposits use `create_instant_static_deposit_quote` and
`create_claim_instant_static_deposit`. The quote contains the real deposit
value, recovery miner fee, signed credit amount, and one zero-confirmation
fulfillment plan. A claim needs the wallet identity signature and the static
address private key share. The server encrypts the share before storage.
The operator reserves the static address and amount while it sends the Spark
credit. This implementation pays the full quoted credit at once; it has no
second payment after confirmation.

Both `SSP_INSTANT_MAX_OUTSTANDING_SATS` and `SSP_INSTANT_MAX_DEPOSIT_SATS`
must be nonzero. Both default to zero, which disables new advances. The
outstanding limit counts Spark credit until the recovery transaction has
three confirmations. Each owner can have one pending instant claim. An
unconfirmed deposit must spend confirmed inputs. These limits bound the
advance; they cannot prevent loss if the deposit is double-spent.

Recovery starts after the deposit has one confirmation. A replacement with
the same address and amount can satisfy the reservation. Missing deposits
or replacements with a different amount keep the advance pending and keep
its budget reserved. A timeout never creates another payout or releases the
budget. Once a recovery signing plan is saved, retries use that exact plan.
A reorganization after signing can therefore require operator investigation.
The background worker continues recovery after restart, including when new
advances have been disabled. Admin status reports outstanding credit and
settlement history reports each pending recovery.

The pinned Breez client has no high-level instant-deposit method. The Rust
acceptance client uses the Spark wire contract to sign the claim; the
unmodified Breez wallet receives the resulting Spark transfer and reads its
standard static-deposit history. See [the acceptance test](../e2e/breez/src/instant.rs).
