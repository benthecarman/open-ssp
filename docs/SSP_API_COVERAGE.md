# SSP API coverage

The SSP accepts GraphQL requests at `/graphql/spark/rc`,
`/graphql/spark/2025-03-19`, and `/graphql`. Financial mutations and
owner-scoped reads require a valid bearer session. Cooperative withdrawal
quotes also require a session because they check leaf ownership. Challenge
handlers, other fee estimates, and inert webhook compatibility handlers are public.

The server accepts the aliases and compressed request bodies generated by the
Spark JavaScript SDK. This table states the current behavior. A
compatibility-only operation returns the expected response shape but does not
complete the underlying financial action.

| Operation | Status | Current behavior |
|---|---|---|
| `get_challenge`, `verify_challenge` | Supported | Single-use five-minute challenge and durable 24-hour session |
| `leaves_swap_fee_estimate` | Supported | Returns `SSP_SWAP_FEE_SATS` |
| `request_swap` | Supported and tested | Verifies the funded outbound transfer and completes an atomic Swap V3 counter transfer from exact SSP leaves |
| `request_lightning_send` | BOLT11 and BOLT12 supported and tested | BOLT11 uses a preimage swap. BOLT12 verifies a completed Spark prepayment, tracks the LDK payment, and returns the prepayment after a final failure. |
| `lightning_send_fee_estimate` | Limited | Returns the current zero-fee policy; it is not a route estimate |
| `request_lightning_receive` | BOLT11 supported and tested | Creates a hold invoice for the wallet hash, redeems wallet-held operator shares with `REASON_RECEIVE`, commits Spark before the LDK claim, and reconciles missed events |
| `request_bolt12_receive` | Supported SSP extension and tested | Creates a fixed-value BOLT12 offer and credits the wallet with a deterministic Spark transfer after LDK receives the payment |
| `transfers`, `user_request` | Supported for SSP-created records | Returns owner-scoped durable swap, Lightning, and withdrawal state |
| `lightning_receive_quote` | Compatibility only | Returns a signed JSON manifest; the SDK quote flow requires a protobuf `TransferManifest` |
| `static_deposit_quote`, `claim_static_deposit` | Regtest test path | Signs a fixed-value test quote; no production UTXO valuation or completed claim transfer |
| Instant static-deposit operations | Compatibility only | Stores or returns placeholder state |
| Cooperative-exit operations and fee quotes | Supported when configured | Estimates Bitcoin fees, reserves a payout input, verifies the conditional Spark transfer, signs and broadcasts the payout, and recovers Spark leaves after confirmation |
| `FetchCurrentUserToUserRequestsConnection` | Compatibility only | Returns an empty connection |
| Wallet webhook operations | Compatibility only | Returns empty or synthetic results; no delivery queue exists |

## Tested Lightning receive flow

The current end-to-end flow is:

1. Authenticate a standard Spark SDK wallet with the SSP.
2. Call the SDK `createLightningInvoice` method. The wallet creates the
   preimage and stores its threshold shares with the Spark Operators.
3. Pay the returned BOLT11 invoice.
4. Poll the receive request until `TRANSFER_COMPLETED`.

The SSP redeems the shares only as part of the operators' atomic Spark transfer.
The removed SSP preimage extension is not required. Fee-bearing quoted
receive invoices remain unsupported until
the SSP emits the required protobuf manifest.

`cargo regtest test` runs this flow on a fresh local regtest network through the
Rust Breez SDK at revision `c7eecfe`. It uses local Electrs for Breez chain
data, two SSP instances, and two `ldk-server` nodes. The wallets send and
receive BOLT11 payments between SSPs. Two wallets also check that an unsafe
internal invoice is rejected before funding, with unchanged balances and no
LDK payment. The test has separate BOLT12 send and
receive flows. It checks Spark balances, offer IDs, LDK payment state, and
preimage hashes. The runner also checks send replay, rejected funding, invoice
expiry, and missed-event recovery after an SSP restart.

Send records use typed statuses and explicit links to their Spark funding.
The intent and idempotency key are durable before LDK submission. See
[submission recovery](LDK_GAPS.md#submission-recovery) for lost replies.

## BOLT12 settlement model

A BOLT12 offer does not give the SSP a payment hash before the invoice-request
exchange. Therefore, BOLT12 sends cannot use the BOLT11 hash-locked Spark
transfer. The wallet first sends a completed standard Spark transfer to the
SSP. The SSP then pays the offer. If Lightning reports a final failure, the SSP
returns the same amount with a deterministic transfer ID. This flow is not an
atomic swap. It depends on the SSP refund policy.

For receive, the SSP creates a fixed-value offer. `ldk-server` claims the
Lightning payment, and the SSP then sends the offer amount to the wallet. This
flow is also not atomic because `ldk-server` has no BOLT12 hold-payment API.
Reconciliation repeats the Spark payout safely after a restart. A blinded
route can report an inbound amount that is larger than the offer amount. The
SSP credits only the fixed offer amount.

## SDK compatibility

Cooperative withdrawals require `COOP_BITCOIN_RPC_URL` and a funded, dedicated
Bitcoin Core wallet. Without this configuration, the operations return an
explicit error. The SSP checks the sender, receiver, amount, leaf IDs, transfer
status, and connector inputs before it signs the Bitcoin payout. It stores the
signed transaction before broadcast and retries the same transaction after a
lost reply or restart. Completed requests and input reservations are durable.

Each payout uses one confirmed native SegWit input. The operator must let the
SSP read the withdrawing wallet's leaves. Wallets with private leaf queries
are not supported by this operator API. Quotes expire after five minutes;
wallets can split leaves after a quote to separate the payout and fee. One
withdrawal per wallet can be pending at a time. Batching and automatic fee
bumping are not implemented. See [deployment](DEPLOY.md#cooperative-withdrawals)
for funding and backup requirements.

MutinyNet uses `SIGNET` on the wire. The pinned JavaScript SDK fork maps SIGNET
correctly. The SSP accepts both `lntb` and `lntbs` invoices for TESTNET and
SIGNET sends, since some Signet clients use the older Testnet currency code. Released SDK versions without that fix cannot run
the complete MutinyNet Lightning test.

The pinned Breez SDK does not expose high-level BOLT12 send or receive methods.
Clients can use `request_lightning_send` with an `lno1` offer and an explicit
amount after they transfer the same amount to the SSP. They can use the
`request_bolt12_receive` SSP extension to create a fixed-value offer.

See [ldk-server compatibility](LDK_GAPS.md) for the complete backend boundary.
